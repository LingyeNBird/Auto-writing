# 全自动小说写作系统开发注意事项文档

## 1. 文档目的

本文档用于约束开发过程中的实现方式、工程边界和常见风险，避免项目在实现阶段偏离“个人使用、轻量稳定、可恢复、可检查”的核心方向。

## 2. 总体开发原则

- 不要把个人项目做成企业平台
- 不要为了未来可能的高并发需求提前引入重型基础设施
- 不要把所有逻辑都塞进提示词
- 不要把所有文本都塞进数据库
- 不要让生成过程变成不可回放的黑盒

应优先坚持以下原则：

- 结构清晰
- 状态可恢复
- 资产可检查
- 提示词可版本化
- 每一步可追踪
- 默认采用 TDD 推进核心开发

### 2.1 TDD 为默认开发方式

本项目默认采用 TDD（测试驱动开发）。推荐基本循环：

1. 先写失败测试
2. 再实现最小通过代码
3. 最后做必要重构

对于以下模块，不建议先写成品再补测试：

- 状态机迁移
- 章节上下文包组装
- canon 写入与更新
- 一致性检查规则
- 项目资产保存与恢复

## 3. 项目边界控制

### 3.1 不要过度工程化

当前项目是个人使用，不要默认：

- 多租户
- 高并发
- 微服务
- 消息队列集群
- 分布式工作流平台

如果某个组件的存在只是为了未来可能扩展，而当前没有明确收益，应优先不引入。

### 3.2 保持单体结构

建议在第一阶段维持单体代码仓结构，明确模块边界，但不拆服务。

错误示例：

- 一开始拆成 API 服务、任务服务、向量服务、日志服务、前端服务

推荐做法：

- 一个 Web 进程
- 一个 Worker 进程
- 一个数据库
- 一个项目资产目录
- 用 Docker Compose 统一启动和管理运行环境

### 3.3 以 Docker 为默认运行方式

开发和使用时应明确假设：项目默认通过 Docker 使用。

这意味着：

- 不应把裸机 Python 环境作为唯一运行方式
- 不应把持久化数据留在容器临时层
- 不应让部署步骤依赖大量宿主机手工安装
- 所有关键路径都要考虑容器内路径与宿主机挂载路径的一致性

## 4. 模块边界注意事项

### 4.1 planner 只负责规划

规划模块输出的是：

- 故事 premise
- 总纲
- 角色卡
- 分章计划

它不应该直接写正文，也不应该直接修改运行状态以外的其他模块数据。

### 4.2 canon 模块必须独立

不要把结构化真相管理分散在多个模块里。角色状态、时间线、世界规则、已发生事件、伏笔状态，应集中归口处理。

### 4.3 review 模块只输出结构化结论

审查模块应优先输出：

- 问题类型
- 问题等级
- 证据
- 建议修复方式

不要让 review 模块直接自由重写全文，否则会造成：

- 改动不可控
- 问题来源不清楚
- 成本浪费

### 4.4 rewrite 模块只做定向修复

重写模块输入应是“原文 + 问题列表 + 修复目标”，而不是重新开放式创作整章。

## 5. 提示词资产管理

### 5.1 提示词必须文件化

不要把核心提示词直接写死在 Python 代码中。建议：

- 系统提示词单独存文件
- 各阶段模板单独存文件
- 版本号或更新时间可追溯

### 5.2 提示词分层

建议至少分为：

- 全局系统提示词
- 项目级提示词
- 章节级提示词
- 审查级提示词
- 抽取级提示词

### 5.3 不要把所有上下文都塞进 prompt

上下文越多不代表越稳。应通过检索和上下文包控制输入，只把真正相关的内容送给模型。

## 6. 数据与资产管理注意事项

### 6.1 数据库存状态，文件存正文

建议遵循：

- 状态、索引、记录放数据库
- 长文本与中间产物放文件

### 6.2 所有重要资产都要有版本

以下内容不要覆盖写：

- 故事总纲
- 角色卡
- 章节草稿
- 审查报告
- 事实抽取结果

应采用新版本产物覆盖“当前指针”，而不是物理覆盖旧文件。

### 6.3 文件命名保持稳定

建议固定命名规范，例如：

- `draft_v1.md`
- `draft_v2.md`
- `facts_v1.yaml`
- `review_v1.json`

不要在后期混入随意命名。

### 6.4 Docker 持久化路径必须固定

建议明确区分：

- `/app/data`：项目资产
- `/app/logs`：日志
- `/app/storage`：数据库与检索文件

代码中不要到处硬编码零散路径，统一由配置层管理。

## 7. 状态机实现注意事项

### 7.1 状态必须显式定义

不要用一堆布尔字段拼凑运行状态。应使用明确状态枚举，例如：

- `PLANNED`
- `DRAFTED`
- `FACTS_EXTRACTED`
- `CONTINUITY_CHECKED`
- `REVISED`
- `LOCKED`

### 7.2 状态迁移必须可审计

每次迁移至少记录：

- 从哪个状态迁移
- 迁移到哪个状态
- 谁触发
- 何时触发
- 输入摘要
- 输出摘要
- 是否成功

### 7.3 失败步骤要可重试

可重试的步骤必须具备：

- 明确重试次数
- 最近错误信息
- 对应输入快照
- 上次输出位置

### 7.4 不要隐式修改状态

任何模块都不应绕过 workflow 直接修改核心运行状态。

## 8. 一致性系统注意事项

### 8.1 结构化 canon 和检索记忆必须分开

这是项目最容易做错的地方。

- `canon` 代表项目内部认定的真相
- `retrieval memory` 代表辅助参考材料

不要让检索片段直接变成真相。

### 8.2 事实抽取结果不应直接入库为真相

抽取模型可能会误读或过度总结。建议：

- 抽取结果先进入候选区
- 再经过规则校验或二次确认
- 最后才写入 canon

### 8.3 角色知识边界必须单独处理

很多冲突不是世界观错误，而是某个角色知道了不该知道的信息。这个字段不能只存在于自然语言描述里，最好有结构化表示。

### 8.4 时间线必须可排序

不要只写“后来”“随后”“不久后”这种模糊文本。系统内部需要有可排序的时间/事件顺序字段。

## 9. 模型调用注意事项

### 9.1 必须统一封装模型调用

不要在业务代码中散落各种模型 SDK 调用。应统一通过一层 `LLMClient`。

### 9.2 记录输入与输出摘要

不一定要保存全部原始上下文，但至少要记录：

- 调用阶段
- 使用模型
- 参数
- 输入摘要
- 输出摘要
- 调用耗时

### 9.3 模型失败不要直接中断整个项目

应区分：

- 临时失败，可重试
- 格式失败，可重解析或重提取
- 逻辑失败，进入人工可见问题状态

### 9.4 输出格式尽量结构化

对摘要、抽取、审查等机械任务，尽量要求 JSON/YAML 结构化输出，减少后处理难度。

## 10. 日志与调试注意事项

### 10.1 关键步骤要有结构化日志

至少记录：

- project_id
- chapter_number
- run_id
- current_state
- action
- result
- error

### 10.2 不要只记录报错堆栈

还要记录业务上下文，例如当前正在处理哪个章节、哪一步失败、用的哪个模型。

### 10.3 保持日志可读

日志不是只给机器看的，未来排查问题时开发者自己也要能快速看懂。

### 10.4 容器日志与文件日志同时考虑

建议：

- 控制台输出保留关键运行信息，便于 `docker compose logs` 查看
- 同时写入宿主机挂载的日志文件，便于长期追踪与排查
- 不要只依赖容器 stdout 作为唯一日志保存方式

## 11. 测试建议

这里的测试建议默认建立在 TDD 前提下，而不是项目完成后再集中补测试。

### 11.1 优先测流程而不是只测工具函数

要重点验证：

- 项目创建后目录是否正确初始化
- 状态机是否按预期迁移
- 失败后是否能恢复
- 重跑是否生成新版本产物
- 章节上下文包是否按规则组装

### 11.2 为关键步骤准备固定样本

建议保留少量小型样本项目，用于验证：

- 总纲生成
- 分章生成
- 章节摘要
- 事实抽取
- 冲突检查

### 11.3 对提示词变更做回归验证

提示词更新后，至少应验证：

- 输出字段是否还稳定
- 章节包是否仍能正确生成
- 审查结果是否明显漂移

### 11.4 补充 Docker 运行验证

至少应验证：

- 容器首次启动后能正确初始化目录
- 容器重启后 SQLite 与项目资产仍然存在
- `web` 和 `worker` 都能访问同一份挂载数据
- 在任务执行中途重启 `worker` 后，任务能够继续恢复

### 11.5 缺陷修复必须先补回归测试

当出现以下情况时，应先补测试再修代码：

- 状态机跳错步骤
- 角色设定更新错误
- 时间线顺序错误
- 上下文包漏带或错带关键约束
- 已修复过的问题再次出现

如果某个问题无法被测试稳定复现，应优先改善可测试性，而不是直接跳过测试。

## 12. 文档与命名规范

### 12.1 术语保持一致

以下术语建议固定使用，不要在代码和文档中混用不同名字：

- 项目：Project
- 全局运行：NovelRun
- 章节运行：ChapterRun
- 故事圣经：Story Bible
- 结构化真相：Canon
- 章节上下文包：Chapter Packet
- 一致性问题：Continuity Issue

### 12.2 目录结构稳定

不要在开发中频繁改动项目资产目录结构，否则历史数据和工具链会受到影响。

## 13. 常见错误

应尽量避免以下问题：

- 为了省事，把所有逻辑塞进一个 prompt
- 为了灵活，让多个模块都能改状态
- 为了快，把所有文本都塞进数据库
- 为了“智能”，让 reviewer 直接重写全章
- 为了“以后扩展”，提前加 Redis、Postgres、消息队列和分布式编排
- 为了继续跑下去，忽略关键冲突并强行写下一章
- 把 SQLite、日志或项目资产写进未挂载的容器内部目录
- 让本地开发路径和容器内运行路径各自为政

## 14. 最后原则

这个项目成功的标志不是“看起来用了很多 AI 技术”，而是：

- 能稳定跑完整本书
- 中断后能恢复
- 设定和剧情不轻易打架
- 出问题时能快速定位
- 资产和过程都清楚可查

如果某个设计决定违背了这些原则，即使它听起来更先进，也不应该优先采用。
