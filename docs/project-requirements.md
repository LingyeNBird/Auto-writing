# 全自动小说写作系统项目需求文档

## 1. 文档目的

本文档用于明确个人版全自动小说写作系统的建设目标、使用边界、功能范围和验收标准，为后续设计、开发、测试和迭代提供统一依据。

## 2. 项目背景

用户希望搭建一套可长时间自主运行的小说写作系统，并提供一个简单的 Web 控制界面。用户只需要输入目标章节数，以及可选的主题说明，系统即可自动完成从构思到正文生成再到一致性修正的全过程。

在长篇生成任务中，单轮提示词或简单续写方案通常会出现以下问题：

- 世界观和人物设定前后冲突
- 章节之间缺少因果衔接
- 伏笔埋设后遗忘或提前泄露
- 角色知道了自己本不应知道的信息
- 文风、节奏和叙事视角随章节漂移

因此，本项目的核心不是“快速写一段文本”，而是建立一套可持续运转的长篇写作生产系统。

## 3. 项目目标

### 3.1 核心目标

- 支持用户通过极简输入发起整本小说的自动创作流程
- 建立完整的上下文管理、设定管理、章节管理和纠偏机制
- 在个人使用场景下稳定运行长时间任务，并支持中断后恢复
- 提供一个轻量、可操作、可观察的 Web 控制台

### 3.2 非目标

以下内容不属于第一阶段目标：

- 面向多用户的在线 SaaS 平台
- 高并发任务调度与资源隔离
- 社区协作、评论、发布与订阅功能
- 复杂的富文本编辑器和多人实时编辑
- 一次性追求企业级分布式架构

## 4. 目标用户与使用场景

### 4.1 目标用户

- 个人创作者
- 希望探索自动化长篇写作流程的开发者
- 以 Docker 本地部署和个人自用为主的高级用户

### 4.2 典型使用场景

- 输入小说章节数、题材说明，生成完整长篇草稿
- 查看系统生成的总纲、角色设定、章节大纲和正文版本
- 发现章节冲突后，对某一章进行重跑、重写或锁定
- 中断运行后继续上次的任务，而不需要整本重来

## 5. 产品形态

本项目为个人使用的本地化 Web 应用，核心特点如下：

- 以 Docker 方式本地部署
- 低并发
- 单用户为主
- 长任务运行
- 强调过程控制与资产管理

系统应更像“小说生产控制台”，而非即时聊天工具。

在第一阶段，系统应默认通过 Docker 或 Docker Compose 启动与使用，而不是要求用户手动在宿主机安装完整运行环境。

## 6. 核心业务流程

系统的标准业务流程如下：

1. 用户创建项目并输入章节数
2. 用户可选填写主题、题材、风格倾向或限制说明
3. 系统生成项目初始设定和故事总纲
4. 系统生成角色设定、世界观设定和分章大纲
5. 系统逐章生成正文草稿
6. 系统对每章进行摘要、事实抽取和一致性检查
7. 系统在需要时对章节进行定向修复或重写
8. 系统更新全局设定、时间线和未解决线程
9. 系统完成全书后进行全局一致性收尾与终稿整合

## 7. 功能需求

### 7.1 项目管理

系统应支持：

- 创建项目
- 查看项目列表
- 查看项目详情
- 启动项目运行
- 暂停项目运行
- 恢复项目运行
- 终止项目运行
- 复制项目或基于已有项目创建新项目

创建项目时，至少应输入：

- 项目名称
- 目标章节数
- 可选主题说明

可扩展输入项可包括：

- 题材类型
- 风格偏好
- 叙事视角偏好
- 目标字数范围
- 禁止元素或硬性约束

### 7.2 故事规划

系统应支持自动生成和管理以下内容：

- 故事核心 premise
- 世界观与背景设定
- 角色清单与角色卡
- 核心矛盾和主线目标
- 整体剧情结构
- 分章大纲
- 伏笔与待回收线索
- 结局方向与收束约束

上述规划内容应支持版本化保存，不允许被后续流程直接无痕覆盖。

### 7.3 章节写作

系统应支持逐章写作，并在写作前自动为每章生成上下文包。章节写作至少应具备：

- 章节目标
- 章节冲突
- 角色出场约束
- 最近章节摘要
- 相关设定引用
- 时间线约束
- 本章必须推进的线索

系统应支持为每章保存多个草稿版本。

### 7.4 一致性管理

系统应具备基础一致性检查能力，至少包括：

- 角色设定一致性检查
- 时间线一致性检查
- 世界观规则一致性检查
- 信息边界检查
- 伏笔推进与回收检查
- 主线/支线推进检查

当发现冲突时，系统应：

- 记录冲突内容
- 标记冲突等级
- 关联冲突来源章节
- 触发定向修复流程或进入待人工处理状态

### 7.5 资产管理

系统应把以下内容作为可管理资产保存：

- 项目配置
- 故事总纲
- 角色设定
- 世界观设定
- 分章大纲
- 章节正文
- 章节摘要
- 事实抽取结果
- 一致性检查报告
- 运行日志

资产应可追溯、可查看、可导出。

### 7.6 运行控制台

WebUI 至少应提供：

- 项目概览
- 当前运行阶段
- 当前处理章节
- 章节状态列表
- 失败原因展示
- 冲突列表
- 重跑按钮
- 暂停/继续按钮
- 文档与资产查看入口

### 7.7 故障恢复

系统应具备基础恢复能力：

- 进程中断后能够恢复到最近检查点
- 已完成章节不应重复生成
- 已保存资产不应因重试被意外覆盖
- 对同一章节的重跑应有明确版本区分

## 8. 非功能需求

### 8.1 易维护性

- 系统结构应清晰，避免过度工程化
- 文本资产应尽量可直接查看和备份
- 配置、提示词、模板和生成产物应明确分离
- 代码开发过程应以 TDD（测试驱动开发）为默认实践

### 8.2 可观察性

- 系统应记录关键步骤日志
- 系统应能够显示当前状态、最近错误和处理结果
- 系统应支持按项目和章节定位问题

### 8.3 可恢复性

- 长任务中断后可恢复
- 失败步骤可重试
- 状态应持久化保存

### 8.4 一致性优先

- 在创作速度和稳定性之间，优先保证设定与剧情一致性
- 系统不得为了继续生成而无条件忽略关键冲突

### 8.5 本地优先

- 第一阶段应默认以 Docker 本地部署和本地存储为主
- 不强依赖云端基础设施

### 8.6 Docker 运行要求

- 系统应支持通过 Docker 统一运行环境
- 系统应支持通过 Docker Compose 编排主要进程
- 持久化数据目录必须通过 volume 或 bind mount 挂载到宿主机
- 容器重建后，项目资产、数据库和日志不得丢失
- 不应把运行所需的核心数据只保存在容器内部临时层中

### 8.7 测试驱动开发要求

- 第一阶段开发默认采用 TDD（测试驱动开发）
- 新增核心业务逻辑前，应先编写失败测试，再实现最小可用代码
- 修复缺陷时，应优先补充能够稳定复现问题的测试
- 状态机、上下文组装、事实抽取和一致性检查等核心环节应具备可自动执行的测试覆盖

## 9. MVP 范围

第一阶段建议纳入以下能力：

- 项目创建与运行管理
- 自动生成故事总纲与分章大纲
- 逐章写作
- 章节摘要与事实抽取
- 基础一致性检查
- 定向重写一轮
- 运行控制台
- 文本资产存档
- Docker / Docker Compose 启动方式
- 面向核心流程的 TDD 测试基线

第一阶段可以暂不实现：

- 多用户权限系统
- 复杂编辑器
- 高频实时刷新体验
- 大规模模型并行调度
- 高级出版格式输出

## 10. 验收标准

满足以下条件，可视为第一阶段需求达成：

- 用户可以通过 WebUI 创建小说项目
- 用户只填写章节数和可选主题说明，也能启动完整流程
- 系统能自动生成故事总纲、角色设定和分章大纲
- 系统能逐章生成正文，并对每章保存结果
- 系统能对章节做摘要、事实抽取和基础一致性检查
- 系统能在发现问题时记录冲突并支持重跑或修复
- 系统运行中断后可恢复，不需要整本从头开始
- 用户可以查看关键文档、章节状态和运行日志
- 用户可以通过 Docker 或 Docker Compose 启动系统并保留持久化数据
- 核心流程具备可执行的自动化测试，且开发默认遵循 TDD

## 11. 后续迭代方向

- 更精细的角色状态跟踪
- 更准确的伏笔/知识边界检查
- 更好的终稿整合与全书重审
- 更强的提示词模板管理能力
- 更灵活的模型路由策略
- 导出为多种稿件格式
